# API и интеграции

## Общие правила

- Базовый URL совпадает с origin сайта; Caddy передаёт запросы в Gateway. Новые интеграции используют префикс `/api/v1` (например, `/api/v1/products/all`). Прежние пути без префикса пока сохранены для интерфейса и совместимости.
- Формат запросов и ответов — JSON, кроме выдачи статики.
- Защищённые запросы используют `Authorization: Bearer <JWT>`.
- Gateway после проверки токена передаёт `user-id` downstream-сервису.
- Gateway создаёт новый UUID в заголовке `X-Request-Id`, передаёт его сервису и возвращает в ответе, включая ответы 401. Переданный клиентом `X-Request-Id` заменяется; по значению из ответа можно найти запись запроса в логах Gateway и сервиса.
- UUID передаются строкой в стандартном формате.
- Ошибки Gateway, Auth, Product, Order и Notification имеют JSON-поля `code`, `message`, `fieldErrors`, `requestId`, `timestamp`. `requestId` совпадает с доверенным заголовком `X-Request-Id`; это корреляция запросов, а не распределённый trace ID. `fieldErrors` — объект с ошибками отдельных полей, если есть валидация. Для неожиданной ошибки сервис возвращает безопасное сообщение, а техническую причину пишет только в лог.
- Машиночитаемое описание проверенного ядра клиентских операций находится в [openapi.json](openapi.json). Оно намеренно не объявляет полный охват административных и вспомогательных маршрутов.

Пример ответа Gateway при запросе защищённого ресурса без токена:

```json
{"code":"UNAUTHORIZED","message":"Необходим вход в аккаунт","fieldErrors":{},"requestId":"4cf50b33-44c4-4b34-adc8-1de3970ce8f8","timestamp":"2026-10-05T06:00:00Z"}
```

Для неверного JWT используется `INVALID_TOKEN`, для запрета доступа — `FORBIDDEN`, для неверного пароля — `INVALID_CREDENTIALS`. Ошибки данных обычно имеют `BAD_REQUEST`, неизвестный ресурс — `NOT_FOUND`, неверный JSON — `INVALID_JSON`. Текст внутренних ошибок и сам токен в ответ не включаются. Ассистент и любые будущие сервисы пока не входят в этот общий контракт.

## Административные операции

Пути `/products/admin/**` и `/order/admin/**` предназначены только для роли `ADMIN`. Сейчас Gateway проверяет наличие действительного JWT, а роль перепроверяет владеющий ресурсом сервис. Ролевая проверка на самом Gateway и её контрактные тесты остаются отдельным усилением защиты. Полный список приведён в спеках Product и Order.

## Идемпотентность

Создание заказа принимает `idempotencyKey` в JSON-теле, не заголовок `Idempotency-Key`. Повтор создания с тем же непустым ключом для клиента возвращает прежний заказ. Повтор отмены уже отменённого заказа безопасен. Общий заголовок `Idempotency-Key` для остальных операций пока не реализован.

## Версионирование

Префикс `/api/v1` доступен для существующих HTTP-операций: Gateway удаляет его перед авторизацией и передачей запроса текущим сервисам. Метод, query string, тело запроса, JWT и правила доступа остаются теми же. Старые пути пока работают; дата их отключения не назначена. Несовместимые изменения должны создавать следующую версию, совместимые поля добавляются опционально. OpenAPI пока покрывает 27 клиентских операций, в том числе заказы и возвраты, отзывы, лояльность, уведомления, доставку, магазины и подписку. Дерево категорий описано рекурсивной схемой `CategoryNode`. Frontend генерирует из контракта `src/api/generated.ts`; регистрация, вход, профиль, смена пароля, каталог, категории, карточка товара, отзывы, акции, лояльность, корзина и подробная страница заказа, уведомления и подписка используют типизированный клиент и `/api/v1` для указанных операций. CI проверяет, что файл типов не устарел. Полный охват административных и вспомогательных маршрутов и перенос остальных вызовов ещё не реализованы.
