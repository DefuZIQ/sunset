# Выделение торговой базы SUNSET

Статус на 24 октября 2026: **production переключён**. Product и Order используют `sunset_commerce` с отдельной ролью `sunset_commerce` без суперправ. Покупатели и уведомления остаются в `sunset`, сотрудники — в `sunset_staff`. Product и Order читают профили покупателей через закрытый API Auth, без SQL-запросов к `users`.

## Рабочее переключение

Перед переключением остановлены Gateway, Product и Order, чтобы исключить новые торговые записи. Создан свежий исходный дамп `/home/defuziq/backups/sunset-pre-commerce-cutover-20261024T174957Z.dump` с SHA-256-файлом и проверкой `pg_restore -l`. Только из этой копии скрипт извлечения создал `/home/defuziq/backups/sunset-commerce-cutover-20261024T174957Z.dump`. Исходная база и её торговые таблицы не удалены.

Санитизированный дамп восстановлен в новую БД владельцем `sunset_commerce`; проверены отсутствие таблиц авторизации и уведомлений, вход отдельной ролью по TCP и отсутствие у неё `SUPERUSER`, `CREATEDB`, `CREATEROLE`. До запуска сервисов в старой и новой базах совпали количества: товары 120, заказы 7, позиции заказов 10, остатки по точкам 865, бонусные операции 7, отзывы 1. Product и Order запущены с новыми `COMMERCE_DB*` настройками, прошли healthcheck и запросы каталога/акций; после этого возобновлён Gateway. Публичные URL локального сайта и `t3ch.pro` возвращают JSON и HTTP 200 для `/products/all` и `/order/promotions`.

Секрет торговой роли хранится только в `/home/defuziq/sunset/.env` с режимом `0600`, не в Git. Старую торговую копию в `sunset` нельзя очищать до отдельного подтверждения целостности рабочих сценариев и независимого резервного копирования всех трёх баз. После открытия Gateway откат к старой базе без обратного переноса новых заказов/остатков небезопасен.

## Что проверено

Свежий согласованный `pg_dump -Fc` рабочей базы сохранён как `/home/defuziq/backups/sunset-pre-commerce-drill-20261024T173353Z.dump` (режим `0600`). Скрипт `scripts/test-commerce-extraction.sh` восстановил его во временном PostgreSQL с `--network none`, удалил пять торговых FK к `users` и таблицы клиентской авторизации и уведомлений только в этой копии. Результат: `/home/defuziq/backups/sunset-commerce-rehearsal-20261024T173437Z.dump` (режим `0600`). Оба дампа проверены `pg_restore -l`.

Сверка числа записей до и после удаления таблиц: `products=120`, `categories=27`, `product_stock=865`, `location_stock=865`, `stores=6`, `orders=7`, `order_items=10`, `payments=1`, `deliveries=7`, `loyalty_accounts=2`, `loyalty_transactions=7`, `promotions=3`, `product_reviews=1`, `review_comments=0`, `return_requests=0`. Это состояние дампа, не гарантированно актуальные текущие числа в рабочей базе.

Скрипт `scripts/test-commerce-runtime.sh` восстановил торговый дамп во второй временный PostgreSQL на отдельной внутренней Docker-сети и поднял текущие образы Product и Order с удалённым IAM и профилями. Оба сервиса запустились и прочитали каталог/акции **без таблицы `users`**, подключившись как отдельная роль без суперправ. Проверены владелец таблиц и отсутствие таблиц авторизации/уведомлений. Временные контейнеры и сеть автоматически удалены. Рабочие контейнеры и их подключения не изменены.

В production Compose добавлены необязательные `COMMERCE_DB`, `COMMERCE_DB_USER`, `COMMERCE_DB_PASSWORD` только для Product/Order. При отсутствии значений сохраняется прежнее подключение. `docker compose config` проверен на VM как с текущими настройками, так и с тестовыми значениями новой БД: Auth остаётся на `sunset`, Product/Order направляются в отдельную базу. Тестовый пароль не является рабочим секретом.

Повторить репетицию на VM с Docker:

```sh
sudo sh scripts/test-commerce-extraction.sh /absolute/source.dump /absolute/commerce.dump
sudo sh scripts/test-commerce-runtime.sh /absolute/commerce.dump
```

Исходный дамп создаётся отдельно командой `pg_dump -Fc`; оба файла содержат персональные данные заказов и должны храниться с ограниченным доступом. Скрипт извлечения никогда не удаляет таблицы в рабочей базе и не перезаписывает существующий выходной файл.

## Границы данных после переключения

| База | Назначение | Состояние |
|---|---|---|
| `sunset` | Покупательские учётные записи, адреса, сеансы и сервис уведомлений; временно сохранённая прежняя торговая копия | Работает |
| `sunset_staff` | Сотрудники, MFA, роли и аудит доступа | Работает |
| `sunset_commerce` | Товары, остатки, магазины, заказы, оплаты, доставки, бонусы, отзывы | Работает для Product и Order |

Ежедневное задание `sunset-postgres-backup.timer` выполняет `scripts/backup-postgres-cluster.sh`: комплект из трёх `pg_dump -Fc` и `SHA256SUMS` публикуется только после проверки каждого файла через `pg_restore -l`. Unit обновлён, проверен `systemd-analyze verify` и успешно выполнен; таймер активен. `scripts/test-restore-cluster.sh` восстановил свежий комплект в изолированном контейнере без сети: 41 таблица `sunset`, 22 таблицы `sunset_staff`, 27 таблиц `sunset_commerce`, 120 товаров и 7 заказов. Старый `scripts/backup-postgres.sh` копирует только `sunset` и больше не является единственным рабочим заданием.

После запуска все основные контейнеры здоровы, публичные каталог и акции доступны. Старое предупреждение о заполнении диска на 96% устранено 25 октября: удалены 17 неиспользуемых Docker-образов, рабочие и помеченные для отката образы сохранены. При финальной проверке свободно около 4,9 ГБ (87% занято).

25 октября `scripts/test-split-auth-runtime.sh` прошёл на изолированной Docker-сети с восстановленным комплектом трёх БД: регистрация и вход тестового покупателя, защищённый профиль, вход тестового сотрудника с настройкой MFA и cookie-сеансом, чтение заказов и каталога клиентов в админке, оформление и отмена заказа, возврат остатка и неизменность бонусного баланса. Все тестовые записи существовали **только в копиях** баз; рабочие аккаунты, заказы и остатки тест не изменял. На рабочем публичном API подтверждены HTTP 200 для каталога/акций и 401 для профиля/заказов без авторизации; Product и Order читают клиентский профиль, а Product проверяет сотрудника через закрытые Auth API. Интерактивный вход под существующими владельческими учётными записями не выполнялся.

Откат должен вернуть оба торговых сервиса к прежней базе только после учёта новых записей в торговой БД; простое изменение JDBC URL после приёма заказов приведёт к потере видимости этих заказов.

Отдельно требуется определить поведение при удалении покупателя: прежние межтабличные `ON DELETE CASCADE` не работают между базами. Заказы и финансовые записи должны сохраняться по установленному сроку хранения; персональные поля можно анонимизировать через отдельный процесс, а не каскадно удалять. Пока клиентское удаление не реализовано, этот риск не активен, но его необходимо решить до добавления такой функции.
