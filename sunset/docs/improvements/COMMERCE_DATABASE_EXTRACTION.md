# Выделение торговой базы SUNSET

Статус на 24 октября 2026: **изолированная репетиция пройдена, production не переключён**. Покупатели и торговые данные по-прежнему обслуживаются общей базой `sunset`; сотрудники уже находятся в `sunset_staff`. Product и Order читают профили покупателей через закрытый API Auth, без SQL-запросов к `users`.

## Что проверено

Свежий согласованный `pg_dump -Fc` рабочей базы сохранён как `/home/defuziq/backups/sunset-pre-commerce-drill-20261024T173353Z.dump` (режим `0600`). Скрипт `scripts/test-commerce-extraction.sh` восстановил его во временном PostgreSQL с `--network none`, удалил пять торговых FK к `users` и таблицы клиентской авторизации и уведомлений только в этой копии. Результат: `/home/defuziq/backups/sunset-commerce-rehearsal-20261024T173437Z.dump` (режим `0600`). Оба дампа проверены `pg_restore -l`.

Сверка числа записей до и после удаления таблиц: `products=120`, `categories=27`, `product_stock=865`, `location_stock=865`, `stores=6`, `orders=7`, `order_items=10`, `payments=1`, `deliveries=7`, `loyalty_accounts=2`, `loyalty_transactions=7`, `promotions=3`, `product_reviews=1`, `review_comments=0`, `return_requests=0`. Это состояние дампа, не гарантированно актуальные текущие числа в рабочей базе.

Скрипт `scripts/test-commerce-runtime.sh` восстановил торговый дамп во второй временный PostgreSQL на отдельной внутренней Docker-сети и поднял текущие образы Product и Order с удалённым IAM и профилями. Оба сервиса запустились и прочитали каталог/акции **без таблицы `users`**, подключившись как отдельная роль без суперправ. Проверены владелец таблиц и отсутствие таблиц авторизации/уведомлений. Временные контейнеры и сеть автоматически удалены. Рабочие контейнеры и их подключения не изменены.

В production Compose добавлены необязательные `COMMERCE_DB`, `COMMERCE_DB_USER`, `COMMERCE_DB_PASSWORD` только для Product/Order. При отсутствии значений сохраняется прежнее подключение. `docker compose config` проверен на VM как с текущими настройками, так и с тестовыми значениями новой БД: Auth остаётся на `sunset`, Product/Order направляются в отдельную базу. Тестовый пароль не является рабочим секретом.

Повторить репетицию на VM с Docker:

```sh
sudo sh scripts/test-commerce-extraction.sh /absolute/source.dump /absolute/commerce.dump
sudo sh scripts/test-commerce-runtime.sh /absolute/commerce.dump
```

Исходный дамп создаётся отдельно командой `pg_dump -Fc`; оба файла содержат персональные данные заказов и должны храниться с ограниченным доступом. Скрипт извлечения никогда не удаляет таблицы в рабочей базе и не перезаписывает существующий выходной файл.

## Граница будущего переключения

| База | После переключения | В этом этапе |
|---|---|---|
| `sunset` | Покупательские учётные записи, адреса, сеансы и сервис уведомлений | Без изменений |
| `sunset_staff` | Сотрудники, MFA, роли и аудит доступа | Без изменений |
| Отдельная торговая БД | Товары, остатки, магазины, заказы, оплаты, доставки, бонусы, отзывы | Проверена только временная копия |

Перед реальным переключением необходимы отдельный PostgreSQL-пользователь с минимальными правами и управляемый секрет, новый **свежий** дамп после остановки записей Product/Order, восстановление в отдельную БД, сверка строк и связей, проверка ролей и миграций на этой БД, переключение Product/Order одновременно и проверка клиентского/служебного путей. Исторический репетиционный дамп нельзя использовать для production: после его создания данные могли измениться. На время сверки и переключения Gateway должен не принимать торговые запросы; иначе появляется окно расхождения заказов и остатков. Откат должен вернуть оба сервиса к прежней базе только после учёта новых записей в торговой БД; простое изменение JDBC URL после приёма заказов приведёт к потере видимости этих заказов.

Отдельно требуется определить поведение при удалении покупателя: прежние межтабличные `ON DELETE CASCADE` не работают между базами. Заказы и финансовые записи должны сохраняться по установленному сроку хранения; персональные поля можно анонимизировать через отдельный процесс, а не каскадно удалять. Пока клиентское удаление не реализовано, этот риск не активен, но его необходимо решить до добавления такой функции.
