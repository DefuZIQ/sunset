# Спецификация релиза P0: безопасность и эксплуатационная готовность

## Цель

Закрыть наиболее опасные границы доверия без изменения пользовательских данных, бизнес-процессов и публичного дизайна сайта.

## Объём реализации

### 1. Доверенный контекст пользователя

- Gateway всегда удаляет присланный клиентом `user-id`.
- Для защищённого запроса Gateway валидирует Bearer JWT и устанавливает единственный `user-id` из `sub`.
- Для публичного запроса поддельный `user-id` удаляется; при наличии валидного JWT разрешается безопасно передать вычисленный идентификатор.
- Публичные пути сопоставляются по границе сегмента, чтобы похожий URI случайно не становился публичным.

### 2. Уведомления и подписка

- Список, счётчик и отметка уведомления получают пользователя из заголовка Gateway.
- Frontend больше не передаёт `userId` в URL.
- Публичная подписка принимает email; связь с аккаунтом создаётся только из проверенного JWT.
- Просмотр статуса и отписка доступны только аутентифицированному владельцу.

### 3. Секреты и конфигурация

- JWT и пароли БД поступают из переменных окружения.
- В отслеживаемых production-конфигурациях нет рабочих значений по умолчанию.
- `.env.example` содержит имена переменных и безопасные заглушки.

### 4. Готовность сервисов

- Каждый backend-сервис публикует `/actuator/health`.
- Health endpoint доступен без JWT и не раскрывает лишние детали.
- Production Compose проверяет здоровье сервисов и запускает frontend после готовности Gateway.

### 5. Проверки

- Unit-тест доказывает удаление поддельного `user-id` и установку subject JWT.
- Controller-тесты доказывают использование доверенного заголовка.
- Backend, frontend, production build и smoke-набор проходят целиком.
- Markdown-ссылки и обязательные разделы спецификаций проверены скриптом.

## Вне объёма

- Платёжный провайдер, очередь сообщений, перенос CRA на Vite.
- Разделение общей PostgreSQL на отдельные БД.
- Изменение схемы пользовательских данных.
- Транзакционная переработка бонусов и резервов — отдельный релиз из `ROADMAP.md`.

## План выкладки

1. Создать backup PostgreSQL и проверить ненулевой размер файла.
2. Собрать и проверить ветку локально.
3. Отправить ветку в GitHub.
4. Передать изменённые исходники на сервер и пересобрать затронутые контейнеры.
5. Проверить health endpoints, главную страницу, публичный каталог и защищённый отказ без токена.
6. При ошибке вернуть предыдущие контейнеры/исходники; база не меняется и восстановление не требуется.

## Критерий готовности

Релиз считается готовым только при выполнении каждого пункта [чек-листа](VALIDATION_CHECKLIST.md) и отсутствии падений полного тестового прогона.
