# Спеки возможных улучшений

## P0 — надёжность и безопасность

### SEC-01. Управление секретами

Удалить пароли и JWT-default из отслеживаемых файлов, заменить скомпрометированные значения, добавить `.env.example` без секретов и production secret store. Критерий: поиск по репозиторию не обнаруживает рабочих реквизитов; контейнер без обязательного секрета не стартует.

### ORD-01. Транзакционная лояльность

Начислять бонусы после подтверждения/оплаты, а не при создании. Списание резервировать при оформлении. Отмена создаёт идемпотентные компенсации. Критерий: повторная отмена не меняет баланс, история полностью объясняет итоговый баланс.

### ORD-02. Резервирование остатков

При оформлении атомарно резервировать варианты на ограниченное время, подтверждать после оплаты и освобождать при отмене/таймауте. Критерий: два параллельных заказа не продают последний экземпляр дважды.

### TEST-01. Критический автотестовый контур

Добавить Testcontainers-интеграции для входа, каталога, создания/отмены заказа, бонусов и ролей; frontend E2E на Playwright. Критерий: тесты запускаются одной командой и блокируют релиз при ошибке.

Статус: основной контур выполнен. Playwright проверяет desktop/mobile Chromium; PostgreSQL 16/Testcontainers применяет реальные Liquibase-миграции для Auth, Product и Order Service. Проверены регистрация, профиль, пароль, каталог, отзывы, заказ, бонусы, отмена, компенсация, резерв, конкурентная покупка последнего экземпляра и откат ошибки оплаты. Пять HTTP-контрактных сценариев Gateway дополнены отдельным HTTP E2E с реальными Gateway/Auth/Product/Order и временной БД. Браузерные сценарии доставки, сохранённого адреса, самовывоза и телефона добавлены с детерминированными API-ответами. Сборка образов зависит от всех тестовых задач. Далее — API-01 и OPS-01; реальный геокодер и платёжный webhook пока не покрыты.

## P1 — продуктовые возможности

### ADR-01. Серверная адресная книга

Создать сущности адреса с городом, улицей, домом, корпусом, строением, подъездом, этажом, квартирой, домофоном, индексом, координатами и комментарием. Добавить нормализацию через геокодер и выбор точки на карте. Адреса синхронизируются между устройствами.

### PAY-01. Платёжный сервис

Интегрировать провайдера через payment intent, webhook и возврат. Не хранить реквизиты карты, только токены провайдера и маску. Критерий: статус заказа меняется только по проверенному webhook, возврат связан с исходной транзакцией.

### NOT-01. Реальная доставка уведомлений

Добавить outbox, очередь, шаблоны и каналы email/push. События заказа формируют уведомления асинхронно. Повторы используют backoff и DLQ. Пользователь настраивает категории уведомлений.

### CAT-01. Поиск и фасеты

Выделить индекс поиска, добавить опечатки, синонимы, фасеты по дереву категорий, диапазону цены, рейтингу, полу, размерному типу, цвету и наличию. URL фильтра должен быть воспроизводимым и пригодным для шаринга.

### REV-01. Проверенные отзывы

Связать отзыв с доставленным заказом, добавить фото, модерацию, полезность и ответ магазина. Средний рейтинг пересчитывать асинхронно или транзакционно.

## P2 — качество и масштабирование

### FE-01. Модернизация frontend

Перенести сборку с CRA на Vite, ввести TypeScript, React Query, общий API-клиент, Error Boundary, дизайн-токены и компонентную библиотеку. Разделить крупные страницы на feature-модули.

Статус: CRA/Jest заменены на Vite/Vitest, зависимости обновлены, аудит уязвимостей чистый. Добавлены TypeScript, генерация API-типов и типизированный клиент для регистрации, входа, профиля, смены пароля, каталога, категорий, карточки товара, отзывов, акций, лояльности, расчёта доставки, заказов, возвратов, уведомлений и подписки; существующие JSX-экраны пока не переведены целиком. React Query, Error Boundary, дизайн-токены и декомпозиция экранов остаются следующими итерациями.

### API-01. Контракты

Ввести `/api/v1`, OpenAPI, генерацию типов, единый формат ошибок и trace ID. Добавить contract-тесты Gateway ↔ сервисы.

Статус: Gateway принимает `/api/v1/...`, применяет прежние правила авторизации и передаёт запрос существующим сервисам без префикса. Прежние пути не отключены. Контрактные тесты проверяют публичные и защищённые маршруты, в том числе подписку и уведомления, query string, доверенный `user-id` и одиночный `X-Request-Id`. OpenAPI описывает 27 клиентских операций и рекурсивное дерево категорий; frontend генерирует из него TypeScript-типы, а регистрация, вход, профиль, смена пароля, каталог, категории, карточка товара, отзывы, акции, лояльность, расчёт доставки, заказы, возвраты, уведомления и подписка используют версионированный типизированный клиент. Gateway, Auth, Product, Order и Notification используют общий формат JSON-ошибок с `requestId`; HTTP E2E проверяет его между сервисами. Далее — полный охват маршрутов, перенос остальных запросов и полноценная распределённая трассировка.

### DATA-01. Изоляция БД

Выделить отдельную схему/БД каждому сервису. Обмен данными выполнять API и событиями. Межсервисные отчёты строить через проекции, а не JOIN по чужим таблицам.

### OPS-01. Наблюдаемость

Добавить Actuator health/readiness, Prometheus, Grafana, централизованные JSON-логи и OpenTelemetry. Критерий: по trace ID виден путь запроса от Gateway до БД.

Статус: health, метрики, Prometheus и Grafana работают. Добавлен доверенный `X-Request-Id` и записи с ним в Gateway, Auth, Product, Order и Notification; это основа диагностики, но не полноценный OpenTelemetry trace. Далее — централизованные JSON-логи, trace/span ID и дашборды с alert rules.

### DEP-01. CI/CD и откат

Собирать версионированные образы, сканировать зависимости, запускать тесты и миграционную проверку, разворачивать через staged rollout. Хранить предыдущий образ и документировать rollback.
