# MFA для сотрудников SUNSET — 18 октября 2026

## Объём

В Auth Service добавлен TOTP по RFC 6238 для ролей `ADMIN` и `STAFF`. Сотрудник, уже вошедший в админку, подтверждает пароль, получает секрет для приложения-аутентификатора и завершает настройку шестизначным кодом. После подтверждения все его прежние сеансы отзываются. Следующий вход состоит из пароля и TOTP-кода либо одноразового резервного кода. Старый TOTP-код не может быть использован повторно; допускается расхождение часов на один 30-секундный шаг. Пять неверных попыток дают 15-минутную блокировку фактора. Запрос второго фактора живёт пять минут, и для пользователя действует только последний запрос.

Восемь резервных кодов показываются единожды; в БД остаются только их SHA-256-хеши. Секрет TOTP хранится зашифрованным AES-256-GCM с привязкой к UUID пользователя. Отключение требует действующего сеанса, пароля и второго фактора, а затем отзывает все сеансы.

## Развёртывание и ограничения

Это **поэтапное включение**, а не обязательная MFA для всех сотрудников: учётные записи, не прошедшие настройку, пока продолжают входить по паролю. Не следует заявлять о полном принудительном MFA до отдельного этапа политики/онбординга. Сначала надо безопасно выдать каждому сотруднику резервные коды и предусмотреть процедуру восстановления доступа.

Перед запуском Auth Service необходимо задать `MFA_ENCRYPTION_KEY`: постоянный Base64 от 32 случайных байт. Ключ хранится только в серверном `.env`/секрет-хранилище, резервируется отдельно от БД и не меняется без процедуры ротации: потеря ключа делает существующие TOTP-секреты нечитаемыми. Не включать в Git, логи или браузерный код. После установки миграция V8 создаёт `mfa_totp`, `mfa_recovery_codes`, `mfa_login_challenges` и `auth_sessions.mfa_verified`.

Нужно одновременно обновить Auth Service, API Gateway (точный публичный маршрут `/auth/mfa/login`) и frontend. При ошибке откатить приложение на предыдущие образы/статические файлы, но **не удалять V8 и не терять ключ**. Для аккаунтов с уже включённым MFA старый Auth не проверяет второй фактор, поэтому после реального включения хотя бы одного аккаунта откат Auth требует отдельного решения по безопасности (например, закрытия админки на время исправления).

## Проверки

- Unit: векторы RFC 6238, окно допуска и запрет повтора, шифрование с AAD, API-контракт клиента.
- UI: вход в админку не сохраняет JWT до успешной проверки второго фактора.
- PostgreSQL: регистрация/включение, отзыв прежних сеансов, одноразовость challenge и резервных кодов, отключение и повторный вход — требуется запуск интеграционного теста на Docker/восстановленной БД до установки.
- После установки: health Auth/Gateway, обычный вход клиента, вход сотрудника до включения MFA, настройка тестового сотрудника, TOTP/резервный вход, отказ старого токена, публичные `/` и `/admin/`.

Источники: [RFC 6238](https://www.rfc-editor.org/info/rfc6238/), [OWASP Multifactor Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html).
