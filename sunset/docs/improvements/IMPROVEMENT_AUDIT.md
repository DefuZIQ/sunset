# Полный аудит возможностей улучшения SUNSET

Дата аудита: 24 сентября 2026 года. Аудит сопоставляет продуктовые сценарии, код пяти сервисов, модель данных, контейнеризацию и существующие автоматические тесты. Приоритеты: `P0` — риск безопасности или потери данных, `P1` — заметное влияние на продажи и поддержку, `P2` — развитие и масштабирование.

## Итог

Текущий продукт уже покрывает каталог, профиль, корзину, заказы, бонусы, отзывы, администрирование, уведомления, рассылку и AI-помощника. Главные ограничения находятся не в количестве функций, а в границах доверия между Gateway и сервисами, управлении секретами, транзакционности заказа и эксплуатационной наблюдаемости.

## Безопасность — P0

| Возможность | Наблюдение | Улучшение | Проверяемый результат |
|---|---|---|---|
| Доверенная идентичность | Сервисы принимают `user-id`, а Gateway добавляет его без гарантированного удаления клиентского значения | Удалять входной `user-id`, устанавливать только subject проверенного JWT | Подмена заголовка не меняет пользователя |
| Уведомления | Идентификатор пользователя передаётся в query string | Брать пользователя только из доверенного заголовка Gateway | Нельзя читать и отмечать чужие уведомления |
| Подписка | Клиент может передать произвольный `userId` | Публично принимать email, а пользователя связывать только по валидному JWT | Чужая учётная запись не связывается с подпиской |
| Секреты | В конфигурации присутствуют значения по умолчанию, похожие на рабочие секреты | Обязательные переменные окружения, пример без секретов, ротация | Поиск по отслеживаемым файлам не находит рабочих секретов |
| Зависимости | Старый frontend toolchain содержит известные уязвимости | Миграция CRA → Vite, обновление пакетов, dependency scanning | Нет critical/high уязвимостей в production-зависимостях |
| Администрирование | Авторизация зависит от распределённых проверок | Единая ролевая политика и отрицательные тесты на каждый admin endpoint | Пользователь без ADMIN стабильно получает 403 |

## Заказы, деньги и остатки — P0/P1

- Ввести состояния оплаты, доставки и заказа как отдельные конечные автоматы.
- Начислять бонусы после подтверждённой оплаты или получения; до этого хранить ожидающее начисление.
- Списание бонусов резервировать, а отмену выполнять идемпотентной компенсирующей проводкой.
- Резервировать конкретные варианты товара атомарно и освобождать по таймауту/отмене.
- Добавить payment intent, проверяемые webhook, полный и частичный возврат, журнал событий.
- Хранить неизменяемый снимок названия, цены, скидки, размера, цвета и изображения в позиции заказа.
- Ввести идемпотентный ключ оформления, чтобы двойной клик не создавал два заказа.

## Каталог и поиск — P1

- Поисковый индекс с опечатками, синонимами, морфологией и подсказками.
- Серверные фасеты по полу, дереву категорий, типу размеров, наличию, цвету, цене и рейтингу.
- Управляемые категории без жёстко заданного дерева во frontend.
- Массовый импорт/экспорт, черновики товаров, история изменений и плановая публикация.
- Проверка качества изображений, alt-тексты, WebP/AVIF, responsive images и CDN.
- Связать отзывы с доставленным заказом; добавить фото, модерацию и полезность.

## Клиентский опыт — P1

- Синхронизировать корзину, избранное и адреса между устройствами.
- Добавить серверную адресную книгу, нормализацию геокодером и проверку зоны доставки.
- Добавить доступные состояния загрузки, ошибок и пустых списков; поддержать клавиатуру и screen reader.
- Сохранять фильтры в URL, добавить сравнение товаров и недавно просмотренные товары.
- Сделать прозрачный расчёт цены: товар, скидка, промокод, бонусы, доставка и итог.
- Реализовать управление согласиями, экспорт и удаление данных пользователя.
- Для AI-помощника: grounded-ответы только по каталогу, явное подтверждение действий и оценка рекомендаций.

## Архитектура и данные — P1/P2

- Версионировать API (`/api/v1`), опубликовать OpenAPI и генерировать клиентские типы.
- Ввести единый формат ошибок, correlation/trace ID и строгую валидацию DTO.
- Изолировать БД сервисов; убрать прямые чтения чужих таблиц.
- Передавать доменные события через transactional outbox и брокер; сделать потребителей идемпотентными.
- Ввести миграции Flyway для всех изменений вместо runtime DDL.
- Разделить крупные React-компоненты на feature-модули, добавить TypeScript и общий API-клиент.
- Перенести удалённые вызовы и server state в React Query; добавить Error Boundary.

## Эксплуатация — P0/P1

- Health/readiness endpoints для каждого сервиса и healthcheck в Compose.
- Структурированные логи, метрики Prometheus, дашборды и распределённая трассировка.
- Версионированные образы, CI с тестами/SBOM/сканированием и воспроизводимый rollback.
- Автоматические зашифрованные backup PostgreSQL и регулярная проверка восстановления.
- Ограничения CPU/RAM, таймауты, retries с jitter, circuit breaker и rate limiting.
- Разделить dev/stage/prod, применять least privilege и запускать контейнеры не от root.

## Тестирование — P0/P1

- Интеграционные тесты с PostgreSQL/Testcontainers для заказа, лояльности, ролей и конкурентных остатков.
- Contract-тесты Gateway ↔ сервисы и тесты на подмену доверенных заголовков.
- Playwright E2E для регистрации, покупки, отмены, адресов и админских операций.
- Проверки доступности, визуальной регрессии и responsive layout.
- Нагрузочные сценарии каталога/checkout и chaos-проверки недоступности зависимостей.

## Порядок реализации

1. Текущий P0-релиз: доверенный `user-id`, защита уведомлений/подписок, секреты, healthchecks и регрессионные тесты.
2. Транзакции заказа, бонусов и остатков.
3. CI/CD, наблюдаемость, backup/restore и security scanning.
4. Адреса, платежи и событийная доставка уведомлений.
5. Поиск, отзывы, доступность и модернизация frontend.
6. Изоляция данных и дальнейшее масштабирование.

Подробный объём первого шага закреплён в [спецификации P0](P0_IMPLEMENTATION_SPEC.md).
