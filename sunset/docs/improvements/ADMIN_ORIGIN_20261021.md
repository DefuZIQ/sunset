# Отдельный origin для администрации — 21 октября 2026

## Цель и граница доверия

Публичная панель управления находится на `https://admin.t3ch.pro/`, магазин — на `https://t3ch.pro/`. На локальной VM сохранён вход через `/admin/`, чтобы разработка и аварийная диагностика не зависели от публичного DNS. Ссылки в магазине ведут на отдельный домен только для публичных хостов; ссылка «Перейти в магазин» из админки возвращает на основной домен.

Административный сеанс остаётся host-only cookie `SUNSET_ADMIN_SESSION` с `HttpOnly`, `Secure`, `SameSite=Strict` и `Path=/api/v1`; общий `Domain=.t3ch.pro` запрещён. Для изменяющих запросов Gateway требует привязанный к сеансу CSRF-токен и действующую MFA-сессию. Админский Nginx отклоняет API-запросы с чужим `Origin`, в том числе с `https://t3ch.pro`. На магазинном и публичном API-хосте административные пути Auth (`/auth/admin`, `/auth/mfa`, `/auth/iam`), Product (`/products/admin`) и Order (`/order/admin`) не проксируются ни в версии `/api/v1/`, ни в прежней неверсированной форме. Вход сотрудника со страницы покупателя направляет в админку для MFA. Авторизация покупателя и магазинный API не меняются.

Админский сервер публикует `admin/index.html` в корне и общие сборочные assets; основной сервер перенаправляет `/admin` и `/admin/` на новый домен. Backend Gateway разрешает `https://admin.t3ch.pro` как origin для корректного входа и preflight. Это не расширяет доступ с магазинного origin к админскому хосту: его Nginx возвращает `403` до Gateway.

## DNS, TLS и выпуск

А-запись `admin.t3ch.pro` должна одинаково отвечать `82.22.187.25` на всех авторитетных DNS Spaceweb. При первой попытке `ns2.spaceweb.ru` отдавал парковочный `77.222.62.219`, а `ns4.spaceweb.pro` — VDS; сертификат не выпустился. После синхронизации SOA и A-записей сертификат `sunset-admin-t3ch-pro` получен отдельным webroot challenge через `/var/www/letsencrypt`. Постоянная HTTP-конфигурация сохраняет этот путь для автоматического продления, остальное перенаправляет на HTTPS. Секреты и приватный ключ не хранятся в Git.

Порядок выкладки: тесты frontend и Gateway; сборка Gateway-кандидата и его smoke-тест; размещение статического релиза без переключения `current`; резервная копия текущего Nginx; `nginx -t`; переключение `current`; reload Nginx; проверка HTTPS, cookie/API, запрета чужого origin и магазинного маршрута. При неуспехе вернуть предыдущий Gateway-образ, прежнюю цель `current` и сохранённую Nginx-конфигурацию.

## Проверки

- Frontend unit, typecheck и Vite build, затем desktop/mobile smoke основных страниц.
- Gateway HTTP-контракт допускает новый origin и отклоняет чужой.
- `GET https://admin.t3ch.pro/` показывает SUNSET CONTROL и корректный сертификат.
- `GET /api/v1/auth/admin/session` без cookie возвращает `401`, а запрос с `Origin: https://t3ch.pro` на админский хост — `403`.
- Админские пути на магазинном и API-хосте дают `404`; публичные товары и вход покупателя продолжают работать.
- Продление сертификата проверяется `certbot renew --cert-name sunset-admin-t3ch-pro --dry-run`.

Реальный вход администратора с TOTP и изменение товара/заказа требуют владельца учётной записи; автоматический smoke не должен запрашивать его пароль или резервные коды.

## Фактический выпуск

На VDS активен `/srv/sunset/releases/admin-hardening-20261021`; предыдущие `/srv/sunset/releases/admin-origin-20261021` и `/srv/sunset/releases/admin-cookie-20261018` оставлены для отката. Nginx-конфигурации сохранены как `sunset-admin-origin-20261021-rollback` и `sunset-rollback-20261021`. На VM работают образы Gateway `candidate-admin-origin-20261021` и web `candidate-admin-hardening-20261021`; предыдущие образы помечены `rollback-admin-origin-20261021` и `rollback-admin-hardening-20261021`. База данных не мигрировала и не очищалась.

Сертификат `sunset-admin-t3ch-pro` выпущен до 19 января 2027 года, пробное продление прошло. Перед сборкой Gateway на почти полном диске VM удалён только Docker build cache (9,775 ГБ); данные PostgreSQL и работающие образы не тронуты.

Проверки извне: админская главная `200`; сессия без cookie `401`; чужой Origin на админском API `403`; старые и новые MFA/IAM-пути на магазине `404`; публичный каталог `200`; `/admin/` магазина перенаправляется на новый домен. Desktop/mobile browser smoke прошёл на публичном сайте и на локальной VM. Frontend unit: 72 passed; Playwright: 119 passed, 11 условных пропусков; typecheck/build и Gateway HTTP-тесты прошли.

Реальный вход с TOTP не выполнялся. Некорректный `GET` на POST-only `/auth/mfa/login` сейчас возвращает `500`, тогда как правильный `POST` с пустым challenge возвращает `401`; это отдельный дефект обработки неподдерживаемого HTTP-метода в Auth Service и не влияет на проверенный сценарий входа.
