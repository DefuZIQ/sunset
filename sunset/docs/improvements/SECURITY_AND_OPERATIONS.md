# Спек безопасности и эксплуатации

## Обязательные меры

1. Немедленно заменить все когда-либо опубликованные пароли, API-ключи и JWT-секреты.
2. Удалить рабочие значения из Git-истории, а не только из последнего коммита.
3. Хранить секреты вне образов и логов; выдавать минимальные права.
4. Ограничить административные API ролью на каждом backend-сервисе.
5. Не доверять `userId` из query/body — брать субъект из проверенного JWT.
6. Добавить rate limiting для входа, регистрации, отзывов, подписки и AI-чата.
7. Ограничить размер body, аватара и AI-контекста; валидировать URL изображений.
8. Включить HTTPS, HSTS, безопасные cookie при переходе от localStorage и строгий CSP.

## Резервное копирование

- Ежедневный логический backup PostgreSQL с шифрованием.
- Еженедельный полный backup volume.
- Хранение минимум в двух независимых местах.
- Ежемесячное тестовое восстановление с фиксацией RPO/RTO.
- Backup выполняется перед каждой рискованной миграцией.

## Мониторинг

Минимальные сигналы: доступность web/Gateway, p95 latency, доля 5xx, ошибки входа, неуспешные оформления, расхождение бонусного баланса, отрицательные остатки, размер БД, заполнение диска, возраст последней копии и доступность Ollama.

## Логи и персональные данные

Не логировать токены, пароли, полные телефоны, адреса, содержимое платёжных данных и секреты. Для диагностики использовать маскирование и `traceId`. Сроки хранения должны быть определены для заказов, профиля, логов, уведомлений и подписок.

## Реагирование

Для инцидента фиксируются время, область воздействия, версия, trace ID и принятые действия. Сначала ограничивается ущерб, затем восстанавливается сервис, после чего устраняется первопричина и добавляется автоматическая проверка против повторения.
