# Задачи и релизы SUNSET

## Где ведём работу

- **GitHub Issues** — задачи и дефекты. Для новых записей используйте шаблоны «Ошибка» или «Улучшение».
- **GitHub Projects** — доска с колонками `Backlog`, `Ready`, `In progress`, `Review`, `Done`; добавляйте туда Issues и PR. Отдельный Project не является источником кода.
- **Milestones** — объём планируемого выпуска. Название совпадает с версией, например `v0.1.0`.
- **Pull requests** — единственный обычный путь изменений в `master`. Указывайте Issue, результаты проверки и действия при развёртывании.
- **GitHub Releases** — опубликованные версии с тегом, заметками и ссылкой на проверенный коммит. Не создавайте релиз только потому, что ветка запушена.

## Первый управляемый релиз (история)

При создании регламента ветка `codex/android-app` опережала `master`. Проверка и объединение выполнены в [PR #2](https://github.com/DefuZIQ/sunset/pull/2); [v0.1.0](https://github.com/DefuZIQ/sunset/releases/tag/v0.1.0) опубликован 28 октября 2026 года. Для дальнейших изменений используйте обычный цикл ниже и [актуальный статус большого плана](sunset/docs/improvements/EXECUTION_STATUS.md).

## Обычный цикл

1. Создать Issue с критериями готовности и добавить его в Project и Milestone выпуска.
2. Создать короткую ветку от актуального `master` (`codex/<тема>`), связать PR с Issue.
3. Дождаться успешного CI: контракт API, backend, frontend, E2E, конфигурация инфраструктуры, сборка образов и quality gate. Проверить функциональность вручную на соответствующей среде.
4. После проверки PR объединить в `master`. Тег формата `vMAJOR.MINOR.PATCH` ставить на конкретный коммит `master`. Первую версию выбрать после инвентаризации фактически установленного кода.
5. Развернуть тот же SHA, выполнить smoke-проверки витрины, админки, API и критического покупательского сценария. Для изменений БД заранее создать и проверить резервную копию всех трёх баз.
6. Опубликовать GitHub Release с автоматически сгенерированными заметками, вручную дополнив их миграциями, известными ограничениями и ссылкой на развёрнутый SHA. Закрыть Milestone после проверки выпуска.

## Особые случаи

- **Hotfix:** отдельная короткая ветка от выпущенного тега или текущего `master`, ускоренный PR с обязательными релевантными тестами; новый patch-тег после проверки.
- **Изменения БД:** сначала совместимая миграция, затем код и только потом удаление старой схемы. Откат приложения не должен предполагать откат заказов или финансовых данных.
- **Android:** веб-изменения появляются без нового APK; изменения нативного кода требуют отдельной подписанной сборки, проверки на устройстве и явного указания версии приложения в заметках релиза.
- **Секреты и персональные данные:** не включать в Issues, PR, артефакты CI и release notes. Тестовые сценарии не должны создавать реальные заказы на production.

Публикация фронтенда и схема туннеля описаны в [документации VDS](sunset/deploy/vds/README.md); разделение БД и проверки восстановления — в [спецификации миграции](sunset/docs/improvements/COMMERCE_DATABASE_EXTRACTION.md).

Для backend-кандидата используйте каталог резервной копии `sunset-cluster-*`, содержащий `sunset.dump`, `sunset_staff.dump`, `sunset_commerce.dump` и `SHA256SUMS`. Сначала проверьте восстановление через `sunset/scripts/test-restore-cluster.sh`, затем запустите `sunset/scripts/test-backend-candidates.sh` с этим каталогом и тегом кандидата. `sunset/scripts/deploy-backend-candidate.sh --check` принимает тот же каталог. Для staging checkout укажите путь к рабочему `.env` через `SUNSET_ENV_FILE`; сценарий сохраняет текущий образ для отката. Сервисы `auth-service` и `staff-auth-service` используют общий образ и переключаются вместе.
